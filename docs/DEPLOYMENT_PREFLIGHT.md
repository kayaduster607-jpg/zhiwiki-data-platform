# 单机部署预检与运维示例

本文适用于团队 `/v1` 服务的单机部署准备；它不是部署验收证明。服务当前依赖单个 API 进程、SQLite 和独立导入 worker，不提供多机高可用。原本地 `/api` 工作台与团队 `/v1` 是两个入口，不应把本地工作台暴露给企业网络，也不能把本地质检接口当作已有团队鉴权能力。

## 只读预检

在实际部署账户下、目录已经由管理员创建后执行：

```bash
python -B -m zhiwiki.service.preflight --config /etc/zhiwiki/team.json --backup-dir /srv/zhiwiki-backups
```

命令只读取显式 JSON 配置和目录元数据，不读取 `.env`、不打开数据库、不创建目录、不启动 worker、不执行备份。不得把密钥放进这个 JSON；参考 `config.team.example.json`，但正式环境必须替换示例 Host 和目录。标准输出是 JSON 检查结果，不包含配置内容与绝对路径；命令退出码 0 仅表示可自动判定的阻断项通过，不代表生产就绪，退出码 1 表示存在阻断项或配置无效。

自动检查 Secure Cookie、非示例主机名、数据目录、最低 512 MiB 空闲空间、分离的备份根目录及解释器存在性。对于当前解释器，仅确认能定位 pypdf，不代表版本合规或 PDF 导入成功；独立 worker 的依赖标为未知。目录权限是当前进程的 `os.access` 结果，不保证部署账户实际写入、文件系统配额或足够的备份容量。

TLS、worker 运行和心跳、外部指标与告警、备份定时和恢复演练全部保留为 `unknown`，须在目标机器实测。

## systemd 示例

`deploy/systemd/` 的 API 和 worker 文件只是模板。部署管理员应先创建受限服务账户，安装经核验的项目与依赖，并按目标机器修改 `/opt/zhiwiki`、`/etc/zhiwiki/team.json` 和 `/var/lib/zhiwiki`。确保 JSON 的 `data_dir` 位于 `ReadWritePaths` 中，解释器与应用对服务账户可读且可执行。`ProtectHome=true` 会阻止使用用户主目录中的路径。单实例运行 API，worker 独立运行；模板不创建用户、不安装或启动服务。

应用只监听回环地址。按 [团队部署手册](TEAM_SERVICE.md) 配置受信任的 TLS 反向代理，覆盖客户端提供的转发头；不要启用 `--local-http`。在目标主机上核实证书、完整请求链路和必要的导入子进程权限后，才能决定是否启用服务。不同 systemd、Linux 发行版和安全策略需要独立测试，模板未在目标环境验证。

## 上线前仍需实测

1. 配置备份计划、备份权限、隔离副本和告警；通过项目的 `backup` 命令生成新快照，并在不同的空目录使用 `restore` 验证数据库、授权、原文与检索。不要只复制运行中的 SQLite 主文件。
2. 记录成功备份时间与恢复演练结果，按照业务目标设置和验证 RPO/RTO；预检通过不等于备份存在或可恢复。
3. 将健康检查、worker 心跳、任务失败、磁盘容量、SQLite busy 与错误率接入外部监控和告警。现有进程内统计在重启后归零。
4. 在目标主机、实际数据和预期并发下运行容量与故障测试；准备异常重启、磁盘不足、租约失效和恢复演练。已有本地压测结果不能外推到任何部署环境。
5. 核实账号授权、操作审计、数据分级、备份加密和保留策略；单机 SQLite 不支持直接增加多个 API worker，不能宣称多机 HA。
